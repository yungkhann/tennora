## 3. Target technical design

### Identity, permissions and private data

- Add a dedicated staff role/active-status model linked to existing Auth IDs. Keep players as independent league records. A legacy account gains no league privileges until deliberately assigned a staff role.
- Next.js verifies identity for every private read/mutation. RLS and narrowly granted RPCs separately check active staff role, trainer team ownership, or the judge's table/day assignment. Authorization never comes from submitted role, actor ID or Auth metadata.
- Business operations use the caller's JWT and derive the actor from `auth.uid()`. A server-only Supabase admin module is permitted solely for Organizer-authorized Auth provisioning/reset/deactivation; it must not become the normal business-data client. Provisioning spans Auth and database APIs, so track pending/active/failed states and support idempotent retries rather than claiming cross-service atomicity.
- Gate signup at the provider as well as removing the route. Retest account confirmation, recovery, rotation, logout and deactivation after changing cookies. Cover new localized staff routes in the proxy matcher and authorization tests. Recheck database active status even with a still-valid JWT.
- Private player fields, trainer contacts, hidden lineups and consent evidence stay outside anonymous tables and events. Publish only approved player fields and consented photos. Use a private Storage bucket and a controlled photo-delivery path with consent-revocation/cache handling. Accounts and players deactivate/soft-delete; historical match participants remain readable.
- Anonymous Realtime uses a separate client without staff auth persistence. It subscribes only to explicitly public-safe projections; authenticated private snapshots are fetched through Next.js. Staff consoles poll a small authorized status endpoint while active; a submit response returns the caller's new private snapshot. This is an explicit change from the PDF's private WebSocket groups.

Prove HTTP-only server refresh plus anonymous Realtime in the first integration spike. This is a proposed server-mediated design, not the default browser-auth setup described in the [Supabase SSR guide](https://supabase.com/docs/guides/auth/server-side/advanced-guide). Define the staff connection indicator from the command/snapshot transport and version freshness; the PDF's socket-specific disabled-button rule must be updated for HTTPS commands. Do not silently expose staff tokens to add private subscriptions.

### League model

The planned relationships are `season -> tour -> stage -> group/entry -> team_match -> singles_game -> game_set -> point_event` and `team -> subteam -> roster membership -> player`. Lineups connect each team match to its selected players. Trainer assignments, dropouts, replacements, ratings, settings versions and scheduling retain history.

Implement the PDF's tables plus explicit season/team registration and roster-history links if needed to preserve eligibility over multiple seasons. Add score-command receipts, public match projections, durable background jobs and photo-consent records. Use UUIDs, timestamps, foreign keys, uniqueness and resource constraints. Model tour rosters separately from locked per-match lineups once their distinction is agreed.

### Authoritative scoring and ratings

1. A judge submits `{commandId, matchId, expectedVersion, command}`; the UI disables a second pending command and never awards an optimistic point.
2. The server validates shape and identity. One database RPC reauthorizes role/table/day/match state, verifies command payload consistency, and checks for an already-processed command before comparing versions.
3. Lock the team match and affected game/set; lock affected player-rating rows in a consistent order. PostgreSQL independently computes and validates the allowed table-tennis transition; accepting a client-computed score is forbidden.
4. Append the event and receipt; update set/game/team result, synchronous Elo/history, required advancement/public projection and audit in the same transaction. At three singles wins, cancel the remaining games exactly once. No-show/empty-slot results follow the signed-off policy and do not create artificial Elo games.
5. Return the committed snapshot/version. Realtime notifications invalidate public snapshots. Failed commands create no partial point, rating or result changes. Duplicate command IDs return their recorded result; reuse with different payloads is a conflict.

Keep a pure, tested TypeScript table-tennis reducer for event replay and transition contracts. Database transition functions remain authoritative even for callers bypassing Next.js. A shared fixture suite and generated command sequences must prove TypeScript/PostgreSQL parity; divergence blocks delivery. Undo appends compensating events and follows the agreed completed-result policy, never deletes points or silently rewrites past K values.

### Live updates and recovery

Use a compact public match projection updated in the result transaction. It contains only published information; no base lineup/player-private tables enter the anonymous publication. Fetch an authoritative snapshot after subscribing, on reconnect/refocus and on version gaps. Ignore stale snapshot responses. Preserve an unacknowledged command ID across a reconnect and reconcile its receipt before allowing another point.

Keep a visible disconnected state and disable scoring while disconnected or stale. Public pages fall back to a cached snapshot every five seconds. Private staff status polling stops when hidden and resyncs on return; it must not cache across sessions. Benchmark the Realtime fan-out design early and switch notification strategy if Postgres Changes cannot meet the target; neither transport becomes the score authority.

Public cached snapshots must be anonymous-only projections, not authenticated responses. Photo publication/consent changes must invalidate cached public data. Use durable jobs for ranking refresh/photo processing with retry/deduplication and visible result revision/pending status; advancing a stage cannot depend on stale queued standings.

## 5. Routes and interface priorities

Canonical public routes have a locale prefix: `/{locale}`, `/ranking`, `/player/[playerId]`, `/seasons`, `/season/[seasonId]`, `/tournament/[tourId]`, `/tournament/[tourId]/matches`, `/tournament/[tourId]/draws/[drawId]`, `/live/[matchId]` and `/scoreboard` beneath that prefix. A tournament in the UI is a tour in the model. `/` redirects to `/ru`; old `/live` links redirect to the appropriate localized center. Decide exact public tournament/match detail URLs in A.

Staff routes: localized `/organizer` (seasons/settings/staff), `/hall`, `/team`, `/team/[teamId]`, `/subteam/[subteamId]`, `/subteam/[subteamId]/tour/[tourId]`, and `/linear-judge`. The PDF's `/team/[id]` description conflates team/subteam; use explicit IDs and terminology. Public match data is separate from protected match-operation controls. Auth callbacks remain unlocalized fixed routes with safe destination handling.

Prioritize four real workflows:

1. Organizer provisions staff, configures a season/tours/stages and registers clubs.
2. Trainer maintains eligible players, selects a tour roster and submits a hidden, locked match lineup.
3. Main Judge assigns/calls/starts matches; assigned Line Judge scores on a landscape tablet, with confirmation and controlled undo.
4. Spectator opens the league homepage and follows standings, player ratings, schedules and live matches without an account.

All screens need loading, empty, validation, success, permission, network and stale-data states. Keep point buttons large, keyboard focus visible, Kazakh characters legible and timestamps in the configured venue timezone. The hall scoreboard emphasizes called/live matches rather than organization onboarding. Installation/PWA does not imply offline scoring.

## 7. Go-live gates and operations

Preserve the PDF's targets as acceptance gates, not statements that the current stack already meets them:

- Generate the agreed 72-subteam event draw/schedule with no duplicate entries, missing placements or resource conflicts.
- Sustain **2,000 viewers and 30 simultaneous simulated matches for 30 minutes**, using real target tablet devices and production-like hosting. Configure adequate simulated tables explicitly; the normal default remains 12. Include three-language public reads, concurrent judge commands, correction and reconnect traffic.
- Measure p95/p99: database commit **100/250 ms**; tablet acknowledgement **300/600 ms**; viewer update **1/2 s**; initial live snapshot **1/3 s**; reconnect/resync **3/8 s**; cached public REST **150/400 ms**. Define measurement start/end points and test geography in A; include Next/serverless and managed-service latency in tap-to-ack measurements.
- Force network loss, duplicate commands, lost acknowledgements, Realtime interruption, staff deactivation and a worker retry. Scores must stay correct; recovery must resync; public polling must work; hidden lineups must stay private.
- Verify HTTPS, secure HTTP-only staff cookies, origin/CSRF protections, rate limits, least-privilege direct database/API access and no admin secret in browser bundles. Test role denials independently of hidden buttons.
- Demonstrate backups with **5-minute RPO, 30-minute RTO, 14 daily and 8 weekly recovery copies**, encrypted off-site. Verify purchased/available managed PITR and export capabilities early; scheduled logical dumps alone do not prove a five-minute RPO. Supabase database backups exclude Storage objects, so back up and restore photos separately. Rehearse Auth, grants/functions/RLS, consent records and Storage recovery into an isolated environment; a database restore must reconcile any newer Storage objects before republication. Record measured times and recovered transaction positions.
- Monitor the **99.9% event-day availability target**, command/commit latency, Realtime connections/lag, job lag and database/storage capacity. Set tested alert recipients and runbooks for venue network loss, judge-device failure and provider outage. Clarify measurement window and incident authority.
- Deploy staging before production; run migrations from a separate privileged deployment context, not normal application credentials. Pin and review package versions; revisit the documented lint dependency advisory. Prove repeatable release and rollback procedures.

Provider plan limits, Realtime fan-out and recovery features are early feasibility checks, not final-week assumptions. If the selected service tier cannot meet a gate, obtain an explicit requirement/cost decision or revise the release date; do not represent the default local setup as production evidence.
